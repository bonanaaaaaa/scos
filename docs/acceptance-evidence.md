# Acceptance evidence

This document maps every P1 scenario in the [PRD](prd/scos-ordering.md#must-have-requirements-p1) to the test or documented, reproducible step that verifies it. It is the evidence for issue #13 (core acceptance and CI coverage).

- **Revision:** first recorded on base `main@75e30db` plus the working tree of branch `chore/issue-13-acceptance-verification`, and updated for #38, which moved the QA suite into `apps/api-acceptance`. Each PR records the exact head commit its evidence was checked against.
- **Missing checks are listed as missing, not as passes.** A scenario without an executable check is marked **Gap**, with the role that owns it.
- **Levels:** _unit_ is a Vitest suite with no database. _integration_ is a developer-owned full-stack or persistence test against real PostgreSQL. _API_ is a QA-owned test over the real HTTP listener against real PostgreSQL. _workerd_ runs the Worker inside workerd, against PostgreSQL through its Hyperdrive binding when marked integration. _documented_ is a reproducible manual step. _CI_ is a workflow step.
- **Owners:** backend-developer owns unit and integration tests and production code. qa-engineer owns `apps/api-acceptance/**`. devops owns CI and the local tooling.

## How to re-run

Follow the [evaluator walkthrough](../README.md#evaluator-walkthrough) for install, configuration and databases. Then:

```sh
pnpm test                # unit suites with 80% coverage gates, plus the Worker in workerd
export DATABASE_TEST_URL=postgresql://scos_test:scos_test@localhost:5433/scos_test
pnpm test:integration    # persistence, full-stack API, Worker over Hyperdrive (developer tests, Vitest)
pnpm test:acceptance     # QA black-box tests of the served API, incl. OpenAPI conformance (Playwright)
```

The integration suites need `DATABASE_TEST_URL`. Without it, or without a reachable test database, they fail rather than skip: [`test/support/database.ts`][db-support] throws for the developer suite and [`environment.ts`][qa-environment] for the acceptance suite, and CI rejects `.skip`, `.skipIf`, `.runIf`, `.todo` and `.only` in integration suites ([`ci.yml`][ci], step "Reject skipped or focused integration tests").

## Concurrency measurement

The measurement is the QA API test [`concurrency.acceptance.test.ts`][qa-concurrency]. It sends 30 `POST /api/v1/orders` requests over the real HTTP listener, at most 10 in flight. There are 24 distinct `submissionId`s plus 6 repeats of one shared ID, 2 units each, against 25 units of stock in Paris only (demand 50 units, destination at the Paris warehouse, zero shipping). It asserts invariants only: no oversell, no negative stock, at most one Order per `submissionId`, and only 201, 422 or 503 with `Retry-After`. It samples PostgreSQL lock waiters from a separate connection during the run.

Command, run three times:

```sh
cd apps/api-acceptance && DATABASE_TEST_URL=postgresql://scos_test:scos_test@localhost:5433/scos_test \
  pnpm exec vitest run test/concurrency.acceptance.test.ts --reporter=default
```

Environment: macOS host, Docker `postgres:18.1-alpine` on port 5433, Node.js v24.15.0, Vitest 4.1.11, revision `75e30db` plus the working tree. All three runs passed.

Reading the reports:

- In each run 12 Orders took 24 of 25 units. The 17 responses with status 201 are those 12 Orders plus 5 repeats of the shared ID returning its Order. The 13 responses with status 422 are `INSUFFICIENT_STOCK`. Stock consumed equals accepted units, and nothing was oversold.
- Warehouse-lock contention was real: up to 9 requests waited on the warehouse row locks at once.
- **There are no latency or throughput targets** ([PRD success metrics](prd/scos-ordering.md#6-success-metrics)). The timings are descriptive only, for one developer machine, and are not a benchmark or a pass/fail threshold.
- **The 503 lock-timeout path was not reached** in this batch (`serviceUnavailable: 0`). ## Hosted-only gaps

These need a real Cloudflare or AWS account and are not verified by any local check:

- Hyperdrive transaction-mode pooling, including the transaction-local lock and statement timeouts, and nothing relying on session state ([ADR 0005][adr-0005], [Workers limitations][obs-workers-limits]).
- Hyperdrive query caching staying disabled, so inventory reads are never stale ([ADR 0005][adr-0005]).
- The telemetry flush and per-request pool close under `ctx.waitUntil` on real Workers, and a deployed Worker with its collector down logging only export warnings ([Workers limitations][obs-workers-limits]).
- Workers Logs and Logpush ingestion, CPU time on the Free plan with a Prisma client per request, and replacing the placeholder Hyperdrive ID (#28).
- Access control for any public deployment ([README limitations][readme-limits]).
- The AWS Lambda handler, flush wiring and warm reuse, deferred to #14 ([observability limitations](observability.md#limitations), [Lambda notes](../apps/api/README.md#notes-for-lambda-deployment-14-deferred)).
- Provisioning and hosted verification: the Hyperdrive design (#28), the pipeline (#15) and the hosted demonstration (#33).

## Open risks

- **The 503 path is not reached over HTTP.** The bounded API batch never hit a lock timeout. The 503 mapping over the real listener is checked only as the documented 500/503 envelope when the database is unreachable ([`routing.acceptance.test.ts`][qa-routing], [`openapi.acceptance.test.ts`][qa-openapi] "database unreachable: 500/503 as documented"). The real `lock_timeout` 503 is covered in process (see [Concurrency measurement](#concurrency-measurement)).
- **A possible flake source in the API telemetry test, now retired.** The QA telemetry test used to inject an in-memory sink into an in-process server, which meant calling the process-wide `registerLogCorrelation()` inside the Vitest worker and sharing that global registration with anything else running there. Since #38 the acceptance suite runs the API as its own process and reads telemetry from OTLP payloads and the process's stdout ([`apps/api-acceptance/test/telemetry.acceptance.test.ts`][qa-telemetry]), so that shared global is gone. Recorded because the risk was real, not because it remains.
- **The curl examples depend on stock.** The README [curl examples][readme-curl] show amounts for a freshly seeded database. Any earlier Order changes stock and therefore the amounts. The automated equivalent is "documented examples are usable against a freshly seeded database" in [`openapi.acceptance.test.ts`][qa-openapi].
- **The fresh-checkout walkthrough is documented, not automated.** CI runs the same install, build and test commands, but not the README steps end to end.
